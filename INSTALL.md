# Install Media Studio Enterprise

Media Studio Enterprise ships as a single Windows installer. It brings its own Python
runtime and a matched ffmpeg and ffprobe, so the machine needs nothing pre-installed to
import decks and videos, transcribe, render narrated MP4s and re-voice videos. This page is for the people who install,
run and update it. Building the installer is covered in `desktop/README.md` (in the
repository); running the app from a source checkout in
[README.md › Develop](README.md#develop).

## Requirements

- **Windows 10 or 11, 64-bit.** No administrator rights: the app installs per-user.
- **WebView2 runtime.** Part of Windows 11. On a machine without it the installer
  downloads it, which needs an internet connection once.
- **Disk space.** The 0.13.0 installer is about the same size as 0.12.0's 184,071,140 bytes
  (176 MB): the same vendored runtime and media binaries, a rebuilt UI; the exact size is
  measured after the build.
  Installed it takes roughly 770 MB, plus your projects and rendered videos.
- **Microsoft PowerPoint** (optional, for `.pptx` decks). With PowerPoint installed,
  slides render at full fidelity, animations included. Without it the engine's
  built-in renderer produces basic slides from the deck's text — not the deck's real
  look. PDF decks need nothing extra.
- **Internet** for Edge TTS narration: those voices are generated by Microsoft's online
  service. **Kokoro**, the other narration provider, runs offline on the machine once its
  model is on disk; the model (about 340 MB) downloads once, on the first Kokoro
  narration, which needs an internet connection that one time. Transcription runs
  locally, on the CPU (the optional NVIDIA CUDA libraries are not bundled).
- **Ollama** (optional): translating the narration when re-voicing a video, and the whole
  AI assistant on the slide editor (writing, reviewing, adapting, translating and pacing
  speaker notes, the deck analysis and the Q&A document), expect a local Ollama at
  `http://localhost:11434` with the studio's model pulled (`gemma4:12b` on a fresh install:
  `ollama pull gemma4:12b`). gemma4 needs a recent Ollama; it was tested on 0.34.4.
- **Git** (optional): only needed to update the app from inside Settings — see
  [Updating](#updating).

### GPU transcription (optional)

Transcription (Whisper via CTranslate2) runs on an NVIDIA GPU when the CUDA 12 runtime
libraries are importable; without them the app logs "GPU transcription failed … retrying on
CPU" and carries on at CPU speed, roughly nine times slower. To enable the GPU, install the
three runtime wheels (about 1 GB) into the app's own Python and restart the backend
(**Restart backend** on the Updates card of the Settings page):

```powershell
& "C:\Media-Studio-Enterprise\python\python.exe" -m pip install -r "C:\Media-Studio-Enterprise\app\requirements-gpu.txt"
```

For a source checkout: `venv\Scripts\pip install -r requirements-gpu.txt`.

## Install

1. Run `Media-Studio-Enterprise_<version>_x64-setup.exe` — the file name carries the
   version it installs.
2. Keep the proposed location. The app installs into
   `C:\Media-Studio-Enterprise\` and adds a Start menu entry and a desktop
   shortcut.

The installer is not code-signed yet, so Windows SmartScreen may ask you to confirm on
first run (*More info* › *Run anyway*). If Media Studio Enterprise is running, the
installer asks to close it first.

**Silent install**, for provisioning scripts (a running instance is closed without
asking):

```
"Media-Studio-Enterprise_<version>_x64-setup.exe" /S
```

**Reinstalling** over an existing install keeps your data (see
[Where your data lives](#where-your-data-lives)): the installer offers to remove the
previous version first, and that removal leaves your data alone too. But read
[Updating](#updating) first if that install has updated itself.

### What lands on disk

```
C:\Media-Studio-Enterprise\
  media-studio-desktop.exe    the app window (named after its Rust crate, not the product)
  uninstall.exe
  app\                        the application: a git checkout of the repo, plus boot.py and bin\ (ffmpeg.exe, ffprobe.exe)
    data\                     your database, settings, projects with their rendered videos, logs (see below)
    assets\                   the music library (music\) and, once downloaded, Kokoro's model (models\kokoro\)
  python\                     the bundled Python 3.12 runtime with every dependency installed
  provisioning\               check-environment.ps1 (see Troubleshooting)
```

## First launch

Start **Media Studio Enterprise** from the Start menu. A splash screen shows the backend
starting — it streams the server's own log lines, and a first launch can take a minute
or two while the media stack loads. When the backend answers, the window switches to
the app.

Sign in with **`admin` / `admin`**. On a fresh install the app then asks you to set a
password of your own before it shows anything else — and it means it: until you do, the
API refuses every request except signing in, signing out and changing the password, so
the default credentials cannot be used for real work even from a script.

Once in, open **Settings**: it is one page of cards. Create accounts for your team on the
**Accounts** card (each new account sets its own password at first login; deactivate an
account to end its access — nothing is ever deleted) and set the password rules on the
**Password policy** card (minimum length, complexity, no username inside the password, a
common-password denylist). Everyone changes their own password on the **Your account** card.

Under the hood, the window runs the backend on `http://127.0.0.1:5680` — the same port a
source checkout uses. If something else already holds 5680, the app picks a free port by
itself; nothing changes for you. Closing the window stops the backend: it is tied to the
window with a Windows job object, so it cannot linger and hold the port, even when the
window is killed from Task Manager.

## Where your data lives

Everything the app creates lives inside the install folder:

| What | Where |
|---|---|
| Accounts, sessions and the audit log | `C:\Media-Studio-Enterprise\app\data\media_studio.db` |
| Settings | `...\app\data\config.json` |
| Projects: the imported deck, PDF or video, its transcript and edit, and every video rendered or re-voiced from it | `...\app\data\projects\<id>\` |
| Logs, cache, temporary files | `...\app\data\logs\`, `cache\`, `temp\` |
| The music library the Timeline's Music lane uses | `...\app\assets\music\` (with its `index.json`) |

Rendered videos are saved with their project, never in a separate folder: the Studio card's
**Output folder** is not used by this edition. The install folder is where the engine writes by default
(`utils/config.py` and `api/store.py` resolve their paths from the app's own folder), and
it is the reason the app installs per-user: the folder has to be writable. When the app fails to start, the splash's failure panel has an **Open data folder** button that opens `app\data\`
in Explorer. A follow-up will move this data to `%LOCALAPPDATA%\com.pentaho.media-studio`;
until then the folder is also what the uninstaller leaves behind (see
[Uninstall](#uninstall)).

Environment overrides can go in an optional `app\.env` file next to `main.py`; it is never
part of an update or an installer. The Ollama server's address is `MEDIA_STUDIO_OLLAMA_URL`
(and its model `MEDIA_STUDIO_OLLAMA_MODEL`); a plain `OLLAMA_URL` has no effect, because the
settings always carry their own `ollama_url` and that wins.

## Updating

The **Updates** card on the Settings page shows the installed commit and branch, checks the
app's Git remote for newer commits, and — for an admin — applies them in place:

1. **Check for updates** runs `git fetch` (45-second limit) and compares the installed
   commit with upstream.
2. **Update now** (admins) fast-forwards the checkout with `git pull --ff-only` and
   installs any new Python dependencies into the bundled runtime, as a background job
   with progress.
3. **Restart now** relaunches the backend in place. The page waits for it to come back
   and reloads itself; after four minutes it explains what to do and offers *Keep
   waiting*.

An update delivers everything in the checkout: the backend **and the built UI**
(`frontend/dist` is committed to the repo). It does not replace the bundled Python
interpreter itself, the window (`media-studio-desktop.exe`) or the vendored media
binaries in `app\bin\` (`ffmpeg.exe`, `ffprobe.exe`) — changes to those, and any new
version number, come with a new installer. After an update, the version shown in the
app's sidebar is the new one while Add/Remove Programs still shows the installer's; that
is expected.

**Install 0.9.1 with its installer — do not apply it through the Updates card.** No
installer before 0.9.1 shipped `ffprobe.exe` (0.9.0's `app\bin\` holds `ffmpeg.exe`
alone), and without a prober the re-voice **and every narrated render** fail on any
machine that has no ffprobe of its own — both decode their narration MP3s through a
library that needs one. `ffprobe.exe` arrives only with the 0.9.1 **installer**: an
in-place update brings 0.9.1's code but never refreshes `app\bin\`, so it leaves both
features as broken as they were. Run the 0.9.1 installer over the old install (on one
that has already updated itself, uninstall it first — your data survives — as
[Things to know](#things-to-know) explains).

An install that was updated in place anyway says so at every start, with a warning in
`app\data\logs\app.log`:

- **On a machine with an ffprobe of its own**, the app pairs the shipped ffmpeg with that
  prober and keeps working. The warning names the two binaries, their versions and their
  paths, and asks for the installer.
- **On a machine with none**, the warning says that `app\bin` has no `ffprobe.exe` and
  that the re-voice and every narrated render will fail until the installer is run — and
  they do, at their first decode, with `[WinError 2]` in the job's log.

### What in-app updates need

- **`git` on PATH** on the machine. Without it Settings says so ("git is not installed
  on this machine, so the app cannot self-update") and the app otherwise works
  normally. `winget install -e --id Git.Git` adds it.
- **Access to the app's Git remote.** The remote is the public GitHub repository
  `jporeilly/Media-Studio`, so in-app updates need no Git credentials, only a connection
  to github.com. Git runs with prompts disabled, so a machine that cannot reach it sees
  **"Could not reach the Git remote"** right away rather than hanging; such a machine is
  updated by running a newer installer instead.

### Things to know

- **Prefer the Updates card over reinstalling** — except for a release that changes
  `app\bin\`, as 0.9.1 does (see above). Running an installer over an install
  that has updated itself rewinds `app\` to the installer's commit, and files an earlier
  update had added stay behind as untracked files — which can block the next `git pull`
  if upstream added those same files in between. To move to a new installer cleanly,
  [uninstall](#uninstall) first (your data survives, see below), then install.
- **Installs from the first (2026-09-13) installer:** the very first in-app update also
  brings the fix for restarting from a path with spaces, but that first restart is still
  performed by the old code and does not come back. Close the app, start it again, and
  every update after that restarts cleanly.
- **Leave the checkout alone.** An edited file under `app\` makes `git pull --ff-only`
  refuse, and Settings shows git's message.

## Uninstall

Use *Add or remove programs* (or run `uninstall.exe` in the install folder). If the app
is running, the uninstaller asks to close it.

**What is left behind.** The uninstaller removes only the files the installer laid down,
so it leaves:

- `app\data\` — your database, settings, projects with their rendered videos, logs;
- `app\assets\` — the music library and Kokoro's downloaded model;
- on an install that updated itself, the files those updates pulled in.

The uninstaller's **"Delete application data"** checkbox does not cover any of that: it
clears `%LOCALAPPDATA%\com.pentaho.media-studio` (WebView2's browser cache) and nothing
else. This is a known limitation, tracked together with the data-folder move above.

**To remove everything by hand:** copy anything you want to keep out of
`app\data\projects\` (projects and their rendered videos) and `app\assets\music\` (the
music library), then delete the install folder — in PowerShell:

```powershell
Remove-Item -Recurse -Force "C:\Media-Studio-Enterprise"
```

Reinstalling without deleting the folder keeps your accounts, settings, projects, videos
and music.

## Troubleshooting

**The window shows the splash but never the app.** The splash streams the backend's
log; after 45 seconds it says a first launch can take a while, and after four minutes
— or as soon as the backend process dies — it shows a panel with the last log lines and
four buttons:

- **Try again** restarts the backend in place. A port held for a moment, an antivirus
  scan or a slow disk usually clear on a second attempt.
- **Save report** writes `startup-report.txt` (version, resolved paths, the backend's
  output) into `app\data\` and reveals it in Explorer — attach it to a support request.
- **Copy details** puts the same report on the clipboard.
- **Open data folder** opens `app\data\`.

**Check what the machine is missing.** The installer ships a checker that prints one
OK / WARN / FAIL row per dependency and, at the end, the fixes for the rows that have one.
Only WebView2, the bundled Python and its core packages, and an unwritable data directory
are FAILs; ffmpeg, ffprobe, git, Ollama and disk space are
warnings that name the feature they affect:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Media-Studio-Enterprise\provisioning\check-environment.ps1"
```

Add `-Json` for machine-readable output; the exit code is 1 when anything FAILs.

**Port 5680.** The app prefers port 5680 and quietly uses another free port when it is
taken (for instance by `python main.py` from a checkout). Nothing needs configuring; the
address in use appears in the backend's log lines on the splash and in the startup
report (`Uvicorn running on http://127.0.0.1:<port>`).

**Slides come out plain on a machine that has PowerPoint.** The bundled runtime's
PowerPoint bridge (pywin32) can fail to find its DLLs — a known gap listed under
*Known gaps / follow-ups* in `desktop/README.md` (in the repository). The app keeps
working with the basic renderer; find the line "PowerPoint COM failed: … — using Pillow
fallback" in `app\data\logs\app.log` and report it.

**"Could not reach the Git remote" in Settings.** The machine cannot reach github.com (no
network, or a proxy or firewall in the way). Updates on that machine come from a newer
installer — see [Updating](#updating).

## Run from a checkout

Developers, and anyone without the installer, can run the same app from a source
checkout — the backend on port 5680 serving the built UI, or the Vite dev server on
5681: see [README.md › Develop](README.md#develop). The desktop shell itself can run
against a checkout with `npm run tauri:dev` in `desktop/` (see `desktop/README.md` in the
repository).
