# Media Studio Enterprise - Windows desktop installer

A Tauri shell that ships Media Studio Enterprise as a single Windows installer,
with **its own vendored Python runtime** so the target machine needs nothing
pre-installed. The shell starts the FastAPI backend (via `boot.py`, on the
bundled Python), waits for `GET /api/system/health` on **port 5680**, then points
a WebView2 window at `http://127.0.0.1:5680`. The UI is the same React SPA the
browser build serves, so the two cannot drift apart.

This mirrors the proven recipe used by the PDC desktop apps
(`C:\Projects\PDC-Glossary\desktop`, `C:\Projects\PDC-Query\desktop`), adapted
for Media Studio.

---

## Layout

```
desktop/
  boot.py                  desktop backend entry - puts the app root on sys.path
                           (the embeddable runtime's ._pth drops it) and runs
                           uvicorn on api.app:app (== `python main.py --no-browser`)
  package.json             npm scripts (fetch python, stage, build, collect)
  dist/index.html          the splash the window loads first: polls readiness,
                           streams the backend log, then navigates to the server
  scripts/
    fetch-python.ps1       vendor the embeddable Python + pip install requirements.txt
    stage-app.ps1          stage the app tree + frontend/dist + boot.py into vendor/app
    collect-installer.ps1  copy the built *-setup.exe to <repo>/dist
    check-environment.ps1  post-install "can this machine run it?" report
    make-icons.py          generate the icon set + NSIS bitmaps (white P, black tile)
    sign.ps1               optional Authenticode signing (no-op without a cert)
    lib/common.ps1         shared path resolvers (Python exe, app root, data dir)
  src-tauri/
    src/main.rs            shell: path resolution, Tauri commands, spawn/health/quit
    src/server.rs          backend lifecycle: spawn boot.py, drain logs, job object
    tauri.conf.json        bundle config (NSIS, currentUser, resources, icons)
    Cargo.toml, build.rs
    capabilities/default.json
    icons/                 generated - 32/64/128/256 png, icon.ico, nsis-*.bmp
    vendor/                generated by fetch:python + stage:app (git-ignored)
```

## Build

Prerequisites: **Rust** (stable), **Node 18+**, **Python 3.11+** (only to run
`make-icons.py`), and the Windows **WebView2** runtime (present on Windows 11).
Optional: the Windows SDK (`signtool`) for code signing.

```powershell
# 1. Build the frontend the installer bundles
cd C:\Projects\media_studio_enterprise\frontend
npm install
npm run build                     # -> frontend/dist

# 2. Build the installer
cd ..\desktop
npm install                       # installs @tauri-apps/cli
npm run dist                      # frontend build + vendor python + stage + tauri build + collect
```

`npm run dist` runs the whole chain. The individual steps (also run automatically
by `tauri build` via `beforeBuildCommand`) are:

```powershell
npm run build:frontend    # npm --prefix ../frontend run build
npm run fetch:python      # download the embeddable Python, pip install requirements.txt  (SLOW, >1 GB)
npm run stage:app         # copy the app tree + frontend/dist + boot.py into src-tauri/vendor/app
npm run tauri:build       # compile the Rust shell and produce the NSIS installer
npm run collect           # copy dist\Media Studio Enterprise_<ver>_x64-setup.exe to <repo>\dist
```

Icons are already generated and committed; regenerate them only if the branding
changes:

```powershell
npm run icons             # python scripts/make-icons.py
```

### Output & install

- Installer: `C:\Projects\media_studio_enterprise\dist\Media Studio Enterprise_0.1.0_x64-setup.exe`
- Install (double-click, **per-user, no admin**): `%LOCALAPPDATA%\Media Studio Enterprise\`
- **App data**: `%LOCALAPPDATA%\Media Studio Enterprise\app\data\`
  (SQLite `media_studio.db`, `projects\`, `cache\`, `logs\`, `temp\`) and rendered
  output under `...\app\assets\finished\`.

The installer is **per-user (`currentUser`)** on purpose - see *Why per-user*
below.

### Dev loop (no installer)

```powershell
cd C:\Projects\media_studio_enterprise\frontend ; npm run build   # once, so there is a SPA to serve
cd ..\desktop ; npm run tauri:dev
```

`tauri:dev` skips the vendored runtime and uses the `python` on PATH, so activate
the repo venv (which has the requirements) first, or the backend will fail to
import its dependencies.

### Signing (optional)

```powershell
$env:MSE_SIGN_THUMBPRINT = "<sha1 thumbprint of a cert in the Windows store>"
npm run tauri:build
```

Without `MSE_SIGN_THUMBPRINT` the build is unsigned (normal for a dev build);
Windows shows SmartScreen on first run.

### Verify a machine can run it (after install)

```powershell
& "%LOCALAPPDATA%\Media Studio Enterprise\provisioning\check-environment.ps1"
```

## How the recipe works

- **Vendored Python** - `fetch-python.ps1` downloads Python's official Windows
  *embeddable* zip into `src-tauri/vendor/python`, enables `site-packages` in its
  `._pth`, bootstraps pip, and `pip install`s `requirements.txt` into it. A
  vendored tree is just files: what was tested is what ships. A stamp
  (`version + SHA-256 of requirements.txt`) makes it idempotent.
- **Staging** - `stage-app.ps1` copies the flat app tree (`main.py`, `api/`,
  `core/`, `utils/`, `services/`, `__init__.py`) plus `frontend/dist` and
  `boot.py` into `src-tauri/vendor/app`, excluding dev debris and **all runtime
  state** (`data/`, `assets/`, `*.db`, `config.json`, `.env`). It then imports
  the staged tree on the vendored runtime to prove nothing was left out.
- **Bundling** - `tauri.conf.json` maps `vendor/python -> python` and
  `vendor/app -> app` into `bundle.resources`, so the install tree is
  `<install>/python/python.exe` + `<install>/app/...`.
- **Launch** - `server.rs` spawns `python.exe boot.py --port 5680 --app-dir
  <app>`; if 5680 is busy it falls back to an OS-assigned free port (the webview
  loads whichever port was chosen). stdout/stderr are drained on background
  threads so a traceback is never lost, and on Windows the child is put in a
  **kill-on-close job object** so a crash or Task-Manager kill cannot leak a
  uvicorn holding the port and the SQLite lock.
- **Readiness** - `main.rs` exposes `server_ready`, which does an HTTP `GET
  /api/system/health` **from Rust** (a `fetch()` from the `tauri://` splash would
  be cross-origin and silently blocked). The splash polls it, streams the live
  backend log, then navigates to the server URL.
- **Shutdown** - the window-close handler stops the backend immediately; the job
  object is the crash-safe backstop.

## Why per-user (not per-machine like the PDC apps)

The PDC reference apps install **per-machine** to Program Files and redirect
their state to `%APPDATA%` via a `GLOSSARY_STATE_DIR` environment variable the
Rust shell passes in. **Media Studio has no such override**: `utils/config.py`
and `api/store.py` hard-code the data directory to `<app root>/data` (and
`assets/finished`), computed from the module's own location. Under a read-only
Program Files install those writes would fail at import time.

So this installer is **per-user (`currentUser`)**: the whole app tree lands under
the writable `%LOCALAPPDATA%\Media Studio Enterprise\`, and `<install>/app/data`
is writable as-is - satisfying "data lives under the user profile" without
touching backend code.

**To support a per-machine install later**, the backend would first need a
data-dir env override (e.g. `MEDIA_STUDIO_DATA_DIR`) honoured by both
`utils/config.py` and `api/store.py`; the shell would then pass it (pointing at
Tauri's `app_data_dir()`), exactly as the PDC apps do. That is a backend change
with its own tests and is intentionally **not** done here.

## Known gaps / follow-ups

- **ffmpeg is not vendored.** `moviepy`/`pydub` need it at render time, and
  `requirements.txt` ships neither `static-ffmpeg` nor `imageio-ffmpeg`, so
  rendering needs `ffmpeg` on PATH. Add `imageio-ffmpeg` to `requirements.txt`
  (it bundles a binary) or vendor an `ffmpeg.exe` to close this. `fetch-python`
  and `check-environment` both flag it.
- **pywin32 / PowerPoint COM.** `pip install pywin32` into an embeddable runtime
  can leave `win32com` unable to find its DLLs (no `pywin32_postinstall`). The
  app still boots and serves the UI; only the COM-based PowerPoint export is at
  risk. `fetch-python` runs a soft import check and warns.
- **Installer size.** The media stack (onnxruntime, ctranslate2, numpy, pillow)
  makes the vendored runtime large; expect a multi-hundred-MB installer.
- **No auto-update / self-update.** See below.

## Self-update

The plan calls for self-update from Git, but **neither PDC reference app offers
any self-update mechanism** to copy:

- No Tauri auto-updater: neither `tauri.conf.json` declares the `updater` plugin,
  an `updater` config block, or `createUpdaterArtifacts`; there is no
  `tauri-plugin-updater` dependency.
- No git-pull self-update in the shell. The only `git pull` references in the
  reference repos are in end-user docs describing how a *source checkout* is
  upgraded - not anything the packaged app does.

Updating a PDC install today means running a newer installer over the old one
(NSIS upgrades in place; per-user data is untouched because it lives outside the
app tree). This installer follows the same model. Adding real self-update
(Tauri updater against a signed release feed, or a shell-driven `git pull` for a
checkout-based install) would be new work beyond mirroring the reference - flagged
here so it is a decision, not an omission.
