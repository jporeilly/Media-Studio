# Media Studio Enterprise - Windows desktop installer

A Tauri shell that ships Media Studio Enterprise as a single Windows installer,
with **its own vendored Python runtime and ffmpeg**, so the target machine needs
nothing pre-installed. The shell starts the FastAPI backend (via `boot.py`, on
the bundled Python), waits for `GET /api/system/health` on **port 5680**, then
points a WebView2 window at `http://127.0.0.1:5680`. The UI is the same React
SPA the browser build serves, so the two cannot drift apart.

This mirrors the proven recipe used by the PDC desktop apps
(`C:\Projects\PDC-Glossary\desktop`, `C:\Projects\PDC-Query\desktop`), adapted
for Media Studio - with two deliberate departures: the staged app is a **git
checkout**, so the install updates itself from Settings > Updates, and the
install is **per-user**, because the app writes its data inside its own tree.

This page is the build and the mechanics. Installing, first launch, updating
and uninstalling are covered for end users and admins in
[INSTALL.md](../INSTALL.md).

## Layout

```
desktop/
  boot.py                  desktop backend entry - puts the app root on sys.path
                           (the embeddable runtime's ._pth drops it) and app\bin
                           first on PATH, then runs uvicorn on api.app:app
                           (== `python main.py --no-browser`)
  package.json             npm scripts (fetch python, stage, build, collect)
  package-lock.json        pins @tauri-apps/cli, so shell builds are reproducible
  dist/index.html          the splash the window loads first: polls readiness,
                           streams the backend log, then navigates to the server
  scripts/
    fetch-python.ps1       vendor the embeddable Python + pip install requirements.txt
    stage-app.ps1          git-clone the repo's HEAD into vendor/app, overlay boot.py
                           and bin\ffmpeg.exe, verify the stage
    collect-installer.ps1  copy the built *-setup.exe to <repo>/dist (version-checked)
    check-environment.ps1  post-install "can this machine run it?" report
    make-icons.py          generate the icon set + NSIS bitmaps (white P, black tile)
    sign.ps1               optional Authenticode signing (no-op without a cert)
    lib/common.ps1         shared path resolvers (Python exe, app root, data dir)
  src-tauri/
    src/main.rs            shell: path resolution, Tauri commands, spawn/health/quit
    src/server.rs          backend lifecycle: spawn boot.py, drain logs, job object
    tauri.conf.json        bundle config (NSIS, currentUser, resources, icons)
    Cargo.toml, Cargo.lock, build.rs
    capabilities/default.json   the opener scope behind "Open data folder" / "reveal report"
    icons/                 generated - 32/64/128/256 png, icon.ico, nsis-*.bmp
    vendor/                generated by fetch:python + stage:app (git-ignored)
```

## Build

Prerequisites: **Rust** (stable), **Node 18+**, **Git** (`stage-app.ps1` clones
the repo, and the checkout needs a pushed `origin`), **Python 3.11+** (only to
run `make-icons.py`), and the Windows **WebView2** runtime (present on Windows
11). Optional: the Windows SDK (`signtool`) for code signing.

The installer ships the **committed** tree - `frontend/dist` included, because
the built UI is tracked in git (that is what lets `git pull` update the UI on an
install). So the sequence is: build the UI, commit it, push, then build the
installer.

```powershell
# 1. Build the UI and commit it (skip when nothing under frontend/ changed)
cd C:\Projects\media_studio_enterprise\frontend
npm install
npm run build                     # -> frontend/dist + build-info.json (deterministic)
git add frontend/dist ; git commit -m "build: frontend" ; git push

# 2. Build the installer
cd ..\desktop
npm install                       # installs @tauri-apps/cli (pinned by package-lock.json)
npm run dist                      # frontend build + vendor python + stage + tauri build + collect
```

`npm run dist` runs the whole chain. The individual steps (`fetch:python` and
`stage:app` are also run by `tauri build` itself, via `beforeBuildCommand`) are:

```powershell
npm run build:frontend    # npm --prefix ../frontend run build - an unchanged tree stays git-clean
npm run fetch:python      # download the embeddable Python 3.12.8 + pip install requirements.txt
                          # (SLOW the first time, ~600 MB; stamped, so later runs skip it)
npm run stage:app         # git clone HEAD -> src-tauri/vendor/app, overlay boot.py + bin\ffmpeg.exe, verify
npm run tauri:build       # compile the Rust shell and produce the NSIS installer
npm run collect           # copy dist\Media Studio Enterprise_<ver>_x64-setup.exe to <repo>\dist, print its SHA-256
```

### The staging gate

`stage-app.ps1` refuses to stage when the working tree is dirty, when HEAD is
ahead of its upstream, or when the branch has no upstream - and it checks that
before touching the previous stage. The reason is the self-update: the installed
checkout can only `git pull --ff-only` from a commit the remote already has, so
an installer built from unpushed work could never update. A stale UI build trips
the same gate, because `npm run build` on changed sources rewrites
`frontend/dist` and the tree is dirty. `-Force` stages anyway, with warnings:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/stage-app.ps1 -Force
```

That is for exercising the staging step. `tauri build` re-runs the gate through
`beforeBuildCommand`, so a shippable installer needs a clean, pushed tree.

`collect-installer.ps1` then refuses an installer whose file name does not carry
`__init__.py`'s version, or that is older than 30 minutes: a failed `tauri
build` leaves the previous installer in the bundle folder, and collecting it
would ship a stale artifact under a new name.

Icons are already generated and committed; regenerate them only if the branding
changes:

```powershell
npm run icons             # python scripts/make-icons.py
```

### Output & install

- Installer: `C:\Projects\media_studio_enterprise\dist\Media Studio Enterprise_0.1.0_x64-setup.exe` (~145 MB)
- Install (double-click, **per-user, no admin**; silent: `/S`): `%LOCALAPPDATA%\Media Studio Enterprise\`
  - `media-studio-desktop.exe` - the shell (named after the Cargo crate, not the product), and `uninstall.exe`
  - `app\` - the git checkout (with the committed `frontend\dist`) + `boot.py` + `bin\ffmpeg.exe`
  - `python\` - the vendored runtime
  - `provisioning\` - `check-environment.ps1` + `lib\common.ps1`
- **App data**: `%LOCALAPPDATA%\Media Studio Enterprise\app\data\`
  (SQLite `media_studio.db`, `config.json`, `projects\`, `cache\`, `logs\`, `temp\`)
  and rendered output under `...\app\assets\finished\` - **inside** the install
  tree. See *Why per-user* and *Uninstall and reinstall* below.

The installer is **per-user (`currentUser`)** on purpose - see *Why per-user*
below.

### Dev loop (no installer)

```powershell
cd C:\Projects\media_studio_enterprise\frontend ; npm run build   # once, so there is a SPA to serve
cd ..\desktop ; npm run tauri:dev
```

`tauri:dev` skips the vendored runtime and uses the `python` on PATH, so activate
the repo venv (which has the requirements) first, or the backend will fail to
import its dependencies. A debug build resolves the checkout root from the
crate's location; a release build never does (see *Launch* below).

### Signing (optional)

```powershell
$env:MSE_SIGN_THUMBPRINT = "<sha1 thumbprint of a cert in the Windows store>"
npm run tauri:build
```

Without `MSE_SIGN_THUMBPRINT` the build is unsigned (normal for a dev build);
Windows shows SmartScreen on first run.

### Verify a machine can run it (after install)

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:LOCALAPPDATA\Media Studio Enterprise\provisioning\check-environment.ps1"
```

(PowerShell does not expand `%LOCALAPPDATA%`; use `$env:LOCALAPPDATA`.) From a
checkout the same script is `desktop\scripts\check-environment.ps1`. It prints
one OK / WARN / FAIL row per dependency with a fix attached, and `-Json` emits
the same as JSON. Only WebView2, the bundled Python and its core packages are
FAILs; everything else is a WARN that names the feature it affects.

## How the recipe works

- **Vendored Python** - `fetch-python.ps1` downloads Python's official Windows
  *embeddable* zip (3.12.8) into `src-tauri/vendor/python`, enables
  `site-packages` in its `._pth`, bootstraps pip, and `pip install`s
  `requirements.txt` into it (~600 MB). A vendored tree is just files: what was
  tested is what ships. A stamp (`version + SHA-256 of requirements.txt`) makes
  it idempotent. It hard-fails when uvicorn/fastapi do not import, and warns
  about the media stack, pywin32 and imageio-ffmpeg.
- **Staging** - `stage-app.ps1` `git clone`s the local repo's HEAD into
  `src-tauri/vendor/app` and re-points `origin` at the GitHub remote, so the
  install is a pristine checkout that `git pull --ff-only` can fast-forward (a
  partial file copy read as local deletions and blocked every update). The clone
  ships exactly the committed tree - `frontend/dist` included - and nothing
  ignored (`data/`, `assets/`, `*.db`, `config.json`, `.env`, venvs) can leak; a
  belt-and-braces scan throws if any of those reached the stage. It then
  overlays `boot.py` and imageio-ffmpeg's binary as `app\bin\ffmpeg.exe` (both
  git-ignored at the root, so they do not dirty the installed checkout), and
  proves the staged tree imports `api` (hard) and `api.app` (soft) on the
  vendored runtime.
- **Bundling** - `tauri.conf.json` maps `vendor/python -> python`,
  `vendor/app -> app` and the two provisioning scripts into `bundle.resources`,
  so the install tree is `<install>/python/python.exe` + `<install>/app/...`.
- **Launch** - `server.rs` spawns `python.exe boot.py --port 5680 --app-dir
  <app>` with no console window, `MEDIA_STUDIO_NO_BROWSER=1` and
  `PYTHONDONTWRITEBYTECODE=1`; if 5680 is busy it falls back to an OS-assigned
  free port (the webview loads whichever port was chosen). `boot.py` puts the
  app root on `sys.path`, `app\bin` first on PATH (once - the environment is
  inherited across in-app restarts), sets `IMAGEIO_FFMPEG_EXE`, and never
  writes bytecode. stdout/stderr are drained on background threads into a
  40-line ring buffer so a traceback is never lost, and on Windows the child is
  put in a **kill-on-close job object** so a crash or Task-Manager kill cannot
  leak a uvicorn holding the port and the SQLite lock - a backend that restarted
  itself after an update is still inside the job. Paths come from Tauri's
  `resource_dir()` with the `\\?\` verbatim prefix stripped (it is not a legal
  working directory); a release build reports the packaged location when the
  resources are missing rather than falling back to the developer's checkout.
- **Readiness** - `main.rs` exposes `server_ready`, which does an HTTP `GET
  /api/system/health` **from Rust** (a `fetch()` from the `tauri://` splash would
  be cross-origin and silently blocked), off the UI thread. The splash polls it,
  streams the live backend log, then navigates to the server URL.
- **Diagnostics** - the splash says "still starting" after 45 s and gives up
  after 4 minutes - or at once when the backend process has exited - with the
  last log lines and Retry (restart the backend in place), Save report
  (`startup-report.txt` in the data folder, revealed in Explorer), Copy, and
  Open data folder. The report is assembled in Rust, so version, OS and the
  resolved paths are in it even when the page misbehaves.
- **Shutdown** - the window-close handler stops the backend immediately; the job
  object is the crash-safe backstop.

## Why per-user (not per-machine like the PDC apps)

The PDC reference apps install **per-machine** to Program Files and redirect
their state to `%APPDATA%` via a `GLOSSARY_STATE_DIR` environment variable the
Rust shell passes in. **Media Studio has no such override**: `utils/config.py`
and `api/store.py` hard-code the data directory to `<app root>/data` (and
`assets/finished`), computed from the module's own location. Under a read-only
Program Files install those writes would fail at import time.

So this installer is **per-user (`currentUser`)**: the whole app tree lands under
the writable `%LOCALAPPDATA%\Media Studio Enterprise\`, and `<install>/app/data`
is writable as-is - satisfying "data lives under the user profile" without
touching backend code.

**To support a per-machine install later**, the backend would first need a
data-dir env override (e.g. `MEDIA_STUDIO_DATA_DIR`) honoured by both
`utils/config.py` and `api/store.py`; the shell would then pass it (pointing at
Tauri's `app_data_dir()`), exactly as the PDC apps do. That is a backend change
with its own tests and is intentionally **not** done here.

## Uninstall and reinstall

The uninstaller (`uninstall.exe`, also *Add or remove programs*) closes a running
instance (with a prompt; silently under `/S`), deletes **the files the installer
laid down**, removes the shortcuts and the Add/Remove entry, and then removes the
install folder only if it is empty. Because the app writes inside its own tree,
it never is:

- `app\data\` (database, `config.json`, projects, logs, cache) and `app\assets\`
  (rendered videos) are **left behind**;
- on an install that has self-updated, so are the files the updates added (the
  uninstaller knows only the installer's manifest) and the objects `git fetch`
  brought into `app\.git`;
- the NSIS "Delete application data" checkbox does nothing useful for this app:
  it deletes `%APPDATA%\com.pentaho.media-studio` and
  `%LOCALAPPDATA%\com.pentaho.media-studio`, which hold only WebView2's browser
  cache.

Removing everything is
`Remove-Item -Recurse -Force "$env:LOCALAPPDATA\Media Studio Enterprise"` after
the uninstall.

**Reinstalling** (running an installer over an existing install) lays the
installer's files over what is there - after running the previous uninstaller in
place, if that option on the installer's reinstall page is taken; it is the same
manifest-only uninstall. `app\data` and `app\assets` are untouched either way,
so accounts, settings, projects and videos survive. But `app\` is a git checkout:
the installer's `.git` and tracked files **rewind it to the installer's commit**,
while files an earlier self-update had added stay in the working tree as
untracked files - and if upstream has since added those same files, the next
`git pull --ff-only` refuses ("untracked working tree files would be
overwritten"). So: prefer Settings > Updates to move an install forward; to move
to a new installer, uninstall first (data survives), then install.

Both are consequences of the data living inside the install tree, tracked for
the follow-up in *Known gaps*.

## Self-update

The installed app updates itself from Git (`services/updater.py`,
`api/routers/updates.py`, the Updates card in `frontend/src/pages/Settings.tsx`):

- **Check** (any signed-in user): `git fetch` (45 s limit) then
  `rev-list --count HEAD..@{u}`; the card shows the installed commit and branch,
  the latest upstream commit and how many commits behind the install is.
- **Update now** (admins): a job that runs `git pull --ff-only` and then
  `pip install -r requirements.txt` with the running interpreter - the vendored
  `python\python.exe` in a packaged install, the venv in dev.
- **Restart now** (admins; *Restart backend* is available at any time): the
  backend relaunches itself in place - on Windows through `subprocess` with
  proper argv quoting, so an install path with spaces
  (`...\Media Studio Enterprise\`) works - keeping the shell's log pipe attached.
  The page waits for `/api/system/health`, reloads when it answers, and after
  four minutes says what to do and offers *Keep waiting*. The new process is
  still inside the shell's job object.

What a pull delivers: everything in the checkout - backend code **and** the
built UI, since `frontend/dist` is committed. What it cannot deliver: a new
Python interpreter (only packages, via pip), a new shell exe, a new
`bin\ffmpeg.exe`, or the exe's file version (compile-time; `VERSION.md` explains
why a version bump implies a new installer).

Requirements on the machine:

- `git` on PATH (`check-environment.ps1` has a row for it). Without it the card
  says "git is not installed on this machine, so the app cannot self-update" and
  everything else works.
- Credentials for the remote. The remote is the **private** repo
  `jporeilly/media-studio-enterprise`, so self-update works on machines whose
  Git credentials can read it (the team's own). Git runs with
  `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never` - the backend has no
  console to answer a prompt in - so a machine without credentials gets
  "Could not reach the Git remote: ..." within the timeout and is updated by
  running a newer installer.

One-time note: an install from the first (2026-09-13) installer restarts its
very first update with the *old* code, whose `os.execv` broke on the space in
the install path; that restart does not come back. Close and relaunch the app
once; every restart after it works.

## Known gaps / follow-ups

- **Data lives inside the install tree.** `utils/config.py` and `api/store.py`
  resolve `data/` and `assets/finished` from the app root, which forces the
  per-user install and gives the uninstall/reinstall behaviour above. The
  follow-up is a data-dir env override (e.g. `MEDIA_STUDIO_DATA_DIR`) honoured by
  both, with the shell pointing it at `%LOCALAPPDATA%\com.pentaho.media-studio`
  (Tauri's `app_data_dir()`), exactly as the PDC apps do - a backend change with
  its own tests.
- **ffprobe is not vendored.** `stage-app.ps1` ships imageio-ffmpeg's
  `ffmpeg.exe` only. The engine calls `ffprobe` for media durations and chapter
  markers (`core/video_creator.py`, `core/video_importer.py`) and falls back
  where it is optional (the re-voice trailing pad falls back to `apad`); a
  customer machine without `ffprobe` on PATH loses whatever depends on it, which
  has not been exercised end to end. Vendoring both (`static-ffmpeg` ships
  ffmpeg + ffprobe) would close it.
- **pywin32 / PowerPoint COM.** `pip install pywin32` into an embeddable runtime
  can leave `win32com` unable to find its DLLs (no `pywin32_postinstall`). The
  app still boots and serves the UI; only the COM-based PowerPoint export is at
  risk (the exporter falls back to a basic Pillow renderer). `fetch-python` runs
  a soft import check and warns.
- **Installer size.** ~145 MB to download, ~600 MB of vendored runtime on disk
  (onnxruntime, ctranslate2, numpy, pillow, plus the 84 MB ffmpeg).
- **Unsigned.** `sign.ps1` is a no-op without `MSE_SIGN_THUMBPRINT`; SmartScreen
  warns on first run.
- **Private remote.** Self-update reaches only machines with credentials for
  `jporeilly/media-studio-enterprise`; a customer install is updated by
  installer until the repo (or a release feed) is public.
