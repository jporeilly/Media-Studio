## [Unreleased]

- [fix] **The re-voice mux can no longer hang, and the engine's own code no longer needs an ffprobe.** 0.9.0's mux carried a ten-minute hang on every machine without an ffprobe of its own. The chain: `_revoice_video` muxed without a duration → `replace_video_audio` probed for one → `_probe_duration` spawned a **bare `ffprobe`** → **0.9.0 shipped none** (`app/bin/ffmpeg.exe` only) → the probe answered `None` → `_build_replace_audio_cmd` emitted the unbounded `-af apad` → **the bundled ffmpeg 7.1 never finishes it**. Measured against the shipped binary with a 5 s picture and a 3 s narration: `apad=whole_dur=5.000` exits 0 in **0.1 s**, a bare `apad` was **still running when it was killed at 45 s**, leaving a **48-byte `ftyp` stub with no `moov`**, and only the mux's own `timeout=600` would have ended it, ten minutes in. **A clean 0.9.0 install never got that far**: the re-voice decodes every sentence before it muxes, those decodes need a prober as well, and the job died at the first of them with `[WinError 2]` (the next entry). The hang stood behind that failure rather than in front of it, so **this entry on its own does not make a clean machine re-voice — the next one does**; what it does is fix the mux on its own terms, so that the mux no longer depends on anything the host has installed and cannot hang on any length it is handed. The dev box showed neither failure: its separately installed ffmpeg **8.0.1** puts an ffprobe on PATH, and does **not** stall on a bare `apad` either (exit 0 in 0.2 s). What changed: **(1) the mux measures the picture itself and pads to the larger length** — `pad_seconds` takes the larger of ffmpeg's measurement of the file being muxed and the length the job offers. What the job can offer is **not the picture's length**: with a cut it is the edit's sum of kept ranges, but with no cut it is the extracted `audio.wav`'s (and `record["duration"]` is faster-whisper's measurement of that same WAV), so a first draft of this fix that trusted it alone turned a 10.00 s picture whose sound stopped at 6.01 s into a **6.01 s re-voice, with a success and no warning** — caught in review, measured on both binaries, and now 10 s. The larger, because a pad that overshoots costs one `-shortest` trim while one that falls short silently deletes picture; the job's number still decides when ffmpeg cannot measure the file. **(2) the probe asks ffmpeg** — `_probe_duration` reads ffmpeg's own `  Duration:` line (0.04 s; 0.04 s to say "cannot tell"), same signature and `None` contract, **anchored on its two-space indent and the comma after it**, because the input's Metadata block is printed first and a `comment: Duration: 596523:14:07.99` tag was read as 2,147,483,647.99 s and padded to (the stall again, on the bundled 7.1); and `usable_duration` refuses anything longer than a week (`MAX_MEDIA_SECONDS`), so a bad number from any source means no pad, never an unbounded one. **(3) the unknown branch is safe by construction** — `None`, `0`, negative, unparseable, `inf`, `nan` and absurd lengths all emit **no `-af` at all** (the mux then ends with the shorter stream: finite and visible, where the old command hung). The docstring that claimed "`-shortest` still bounds the output to the video" is gone. **The same class swept out of the rest of the engine:** `core/video_importer.py`'s chapter read, keyframe fallback and `get_video_duration` spawned bare `ffprobe`s and `ffmpeg`s — all reachable only through `import_video`, **which nothing in the app calls** (the product's video path is `services/transcription.py`, which never reads chapters), so this is the sweep's fix, not a customer-visible one; `core/pptx_exporter.py`'s PDF fallback and the re-voice's `atempo` squeeze spawned a bare `ffmpeg` each. All now run the resolved `FFMPEG_PATH` or refuse cleanly. The engine reads duration and chapters out of ffmpeg's own header, so **its code never needs a prober on any machine**; the `ffprobe.exe` the installer now ships is for pydub's decodes alone. `core/video_creator.py`, `core/video_importer.py`, `core/pptx_exporter.py`, `services/processing.py`, `services/revoice.py`, and the docstrings in `services/narration.py` and `services/waveform.py`. Tests: `tests/test_no_bare_ffmpeg.py` (new, **2** — an AST sweep of `core/` and `services/` for a bare `ffmpeg`/`ffprobe` as `argv[0]` of a list or tuple, or as a shell command to `subprocess`, `os.system` or asyncio — **written out or hoisted into a module or local string constant** — plus a planted-file check of every shape; its docstring lists what it still cannot see), `tests/test_generation_options.py` (**+36** — the pad invariant over eleven lengths; the mux measuring the picture and padding to the larger over five measured/told combinations, with the probe answered in its real call shape; `pad_seconds`; the one-week bound; a duration-shaped metadata tag; the no-ffmpeg refusal asserted by its own log line, not by a `False` the catch-all also returns; and **six real-binary checks, each parametrised over both the machine's ffmpeg and the bundled 7.1** when the app is installed, skipped where there is no real ffmpeg: an unknown-length mux completes, a known length keeps the whole picture, **a picture longer than its audio keeps all of it**, a bogus duration tag neither fools the probe nor stalls the mux, the probe answers with `PATH` emptied, and chapters are read with no ffprobe), `tests/test_revoice_sync.py` (**+7** — the measured picture wins over the job's number, a longer belt raises it, an unmeasurable picture falls back to it), `tests/test_revoice.py` (**+1**, and the job's number pinned as the WAV's, not the record's), `tests/test_waveform.py` (docstrings), and the two test fakes that take the new keyword (`tests/test_ai_slides.py`, `tests/test_music_render.py`) — **46 backend tests added**, ruff clean, nothing under `frontend/` touched. Every new check was watched failing against the defect it guards: the unbounded `apad` stalled the real-binary test **on the bundled 7.1 only**, the job's number alone cut the 10 s picture to **6.01 s on both binaries**, and the unanchored regex with no bound stalled the bundled 7.1 at 30 s while 8.0.1 finished in 0.3 s. — #f1-revoice-probe

- [fix] **The installer now carries `ffprobe.exe` — which is what a clean machine needed to re-voice, or to render a narrated deck, at all.** The app is not the only thing that probes. The engine decodes audio with `pydub.AudioSegment.from_file`, and for anything that is not a `.wav` **pydub runs its own prober**: `mediainfo_json` → `get_prober_name` in `pydub/utils.py`, a bare `"ffprobe"` resolved off `PATH`, whatever the app does about its own calls. Ten `from_file` call sites across `core/audio_mixer.py`, `core/video_creator.py` and `services/processing.py` go through it: the re-voice decodes every synthesised sentence, and **every narrated render** decodes every slide's MP3 to build its master track (`create_video` always runs `_build_master_audio`, whose bare `from_file` has nothing around it, so a failed decode fails the render). On a clean 0.9.0 install **both** died at their first decode with `FileNotFoundError [WinError 2]`: **0.9.0 could neither re-voice a video nor generate a narrated deck on a customer machine**, and the entry above changes neither. The fix is the binary, and it fixes **the re-voice and every narrated render** alike: `desktop/scripts/fetch-ffprobe.ps1` vendors it and `stage-app.ps1` stages it as `app\bin\ffprobe.exe` beside ffmpeg. **The version is not free choice.** imageio-ffmpeg — where the shipped ffmpeg comes from — repackages gyan.dev's essentials build, and the pinned archive's own `ffmpeg.exe` is **byte-identical** to the vendored one (87,638,016 bytes, SHA-256 `2ce797a0…af71a3`), so the ffprobe taken out of that same zip is the binary released with it rather than merely a binary of the same number; a full build or the dev box's WinGet 8.0.1 would be a different pair, and 7.1 and 8.0.1 already disagree where this app feels it. Archive `ffmpeg-7.1-essentials_build.zip` (SHA-256 `fa7d4d7e…de24fc`) → `ffprobe.exe` (SHA-256 `436bf025…6873d0`), both pinned and checked, the binary's own `-version` line checked too, and the whole step idempotent and loud: a bad download, a changed archive or a swapped binary is refused, never shipped, and a rejected binary is deleted rather than left in `%TEMP%`. **Both halves of the pair are pinned now.** ffmpeg had arrived only transitively, through `moviepy>=2.0.0`; `requirements.txt` pins `imageio-ffmpeg==0.6.0` (which bundles 7.1), so a runtime rebuild cannot move ffmpeg while ffprobe stays — and the stage step **fails** when the staged pair report different builds, unless `-Force`. Resolution stopped being a PATH race as well: `utils/config.py` takes the pair from the app's own `bin\` **by absolute path**, resolving each binary separately, and points pydub at the resolved prober through the one seam pydub actually honours — `pydub.utils.get_prober_name`. `AudioSegment.ffprobe`, which this module used to set, is an attribute **pydub 0.25.1 never reads**; the ten decodes had been resolving their prober off `PATH` all along, and off the working directory before that, which is where pydub's own `which` looks first. **An in-place update does not deliver the binary, so 0.9.1 must be installed with its installer, not applied through Settings ▸ Updates** — the updater pulls the checkout and never touches `bin\`. A 0.9.0 install updated anyway keeps a `bin\` with no prober, and says so at every start in one of two WARNINGs, to the console and `app.log`. **On a machine with an ffprobe of its own, the mixed pair is allowed, and logged**: the shipped 7.1 ffmpeg runs with the machine's prober (8.0.1 on the dev box). Decoding works — the decode is ffmpeg's; the prober only reports stream metadata — so the foreign prober is not refused, which would break a machine that works; the warning names both binaries, their versions and their paths, and asks for the installer. It fires only when exactly one of the pair is the shipped binary: never when the pair is shipped together, on a source checkout, or when a binary is missing altogether. **On a machine with none, the worst state is not silent either**: the second warning says that `app\bin` carries no `ffprobe.exe` because an in-place update never refreshes it, and that the re-voice and every narrated render will fail until the latest installer is run; before, the first sign was the feature dying with `[WinError 2]`. It stays silent on a source checkout with no shipped ffmpeg, which is a developer's machine, not a broken install; the two warnings never fire together, and `check-environment.ps1` has an `ffprobe` row of its own that says the same. Proven rather than argued, on the vendored runtime: with `PATH` cut to `app\bin` alone, and again in the installed layout with `PATH` holding System32 and nothing else, the shipped prober is found, pydub decodes a real MP3 encoded by the bundled ffmpeg (2,000 ms), `services.processing.calibrate_tts_baseline` measures **25.0** chars/sec instead of falling back to its 15.0 default, and `_build_master_audio` builds a narrated slide's track (2.0 s); take ffprobe away and the re-voice and the render both die with `FileNotFoundError [WinError 2]` again — kept as tests that assert that exact error, so the positive ones cannot quietly stop proving anything (`tests/test_ffprobe_shipped.py`, **39** tests). The timeline's frame-step tooltips, `frontend/src/lib/edit.ts` and a docstring in `services/edit.py` no longer blame a missing prober: a frame is 1/30 s because the timeline never probes the source, not because it cannot. Cost: the installer is about 25 MB larger than 0.9.0's 148 MB (154,761,799 bytes) — `ffprobe.exe` is 83 MB raw but about 23 MB under the installer's LZMA compression — and the exact size is measured after the build: **[TBD at release: measured 0.9.1 installer size]**. Replacing pydub's decodes with the `services/music.py::decode_audio` pattern would win it back and is deferred, not rejected. — #f2-ship-ffprobe

## [0.9.0] - 2026-09-22

Music. A fourth lane on the Timeline carries it: open the library from the lane's header,
add a track at the playhead, then drag the clip to move it, drag its ends to trim it, and
set its level and its fades in the row under the strip. Play hears it under the voice,
and the eye silences it while you listen to the narration alone. Render mixes it in one
more pass that copies the picture, at the level you set, with no ducking and no fade on
the voice. The library is shared by the whole studio, a file is decoded once when it is
uploaded, and a file still used by a project cannot be deleted from under it.

- [feat] **Music can be laid under a video's narration — a studio-wide library, clips placed on the output's timeline, and a render that mixes them under the voice** (porting vertical 6, phase **E4a**: the library, the model and the render pass. **There is no UI yet** — this is the API and the render, driven by `curl` as E1 was; the Music lane itself, its gestures, its inspector and its audition are **E4b**, and 0.9.0 releases the two together. The version stays 0.8.0.) **The library is studio-wide** — shared by every account, like the voices and the studio settings — and sits at `assets/music/`, beside the finished videos where it survives a reinstall: five routes list it, add to it, serve a file and its waveform peaks, and delete from it, taking mp3, wav, m4a, aac, ogg and flac up to 100 MB each, mono or stereo — a file wider than stereo is refused at upload, because the render lays every clip under the voice through one up-mix that keeps mono at its own level and cannot also fold a surround layout properly, and losing a file's rear channels quietly at every render is worse than saying so once. **A file is decoded exactly once, at upload** — to prove it really is audio and to measure its length, sample rate, channel count and the peaks the lane will draw inside a clip — and is never opened to ask anything of it again; nothing on this path runs the ffprobe the packaged app does not have. A name is what a clip refers to, so a name is immutable: an upload of a name the library already holds is refused (rename the file, or delete the old one) rather than silently replacing the file under every project that uses it, and the comparison ignores case, because Windows cannot tell `BED.mp3` from `bed.mp3` and the index must not either. **A clip is a slice of a library file placed on the output's timeline** — `{id, file, at, in, out, gain, fade_in, fade_out}` on the project's edit, at most 200 of them, `at` in the *output's* seconds (the axis the ruler shows, so that when the lane arrives a cut before a clip moves it with the picture, as a Camtasia track does), `in` / `out` the stretch of the file used, `gain` a plain linear factor from 0 to 1, and the two fades linear ramps. - [feat] **A video project can carry an edit — the ranges of its source that are kept — and the re-voice renders it** (porting vertical 6, phase E1: the model and the render, **no UI yet**). This is the first half of "build something like Camtasia": material you can cut. An **edit** is one thing, and it is the whole edit decision list: an ordered list of the `[start, end]` ranges of the project's one source that survive, in source seconds — `"edit": {"version": 1, "keep": [[0, 47.3], [52.3, 341.008]]}` on the project record — and **absent means keep everything**, so every project made before today renders exactly as it did and nothing is migrated. There is no clip object, no track object and no position field, because a split, a trim and a ripple delete are all changes to that one list: a split adds a boundary (two touching ranges where there was one, removing nothing), a trim moves a range's edge, and a ripple delete takes a sub-range out while the ranges either side stay where they are in source time. Position is derived, and that is what makes the second rule possible. **The transcript never moves.** The transcript Save decides that two entries are the same sentence when they have the same `start` and the same `end`, and carries a sentence's adjustments — its offset, mute, voice and speed — across only onto a match; cut ten seconds out of the picture the obvious way, by shifting every later sentence earlier, and every adjustment on every later sentence is dropped by construction, which is the corruption class phase 1 of the narration timeline was built to prevent, inverted. So the transcript stays in source seconds on disk, exactly as Whisper wrote it, and the edit is applied to it as a **projection** — computed by one function in `services/edit.py` at plan time and at render time, so the audition and the render cannot disagree about where a sentence lands. The rule at a cut is simple enough to say in one sentence: **a sentence is kept iff its start lies inside a kept range.** A sentence whose start was cut is left out exactly as a muted one is (the room it occupied goes to the sentence before it); a kept sentence's end is clamped to its range, so nothing is pinned past the output by the projection; every adjustment rides through untouched; and the offset in particular is left as stored, because the engine applies it itself — the pin is `to_timeline(start) + offset`, applied once. **The render is the same re-voice job**, started by the same `POST /api/projects/{pid}/revoice`, with one step in front of it when the edit removes anything: the kept ranges are re-encoded into a picture-only intermediate — `trim` / `setpts` / `concat` in one ffmpeg run at `libx264 -preset ultrafast`, the generate path's own settings, with no frame rate forced so the source's own cadence carries through — and the engine is then told *that* is the source, sees a transcript in a shorter recording and does what it always does; nothing in `_revoice_video` changed. It is a re-encode rather than a stream copy because a stream copy cannot start on the P-frames a cut lands on, and the source's keyframes are two seconds apart (measured), so snapping a cut to a keyframe could miss by more than a sentence; a whole re-encode of a five-minute 1080p source is about **16 s**, cheap enough to do on every render, as a job. Proven on the real 5m41s corpus: cut 47.3–52.3 s and the output is 336.008 s by the WAV arithmetic and 10079 frames / 335.967 s by the picture (the source's video stream is 41 ms shorter than its audio), opening on an I-frame at 0.000. An edit that removes nothing — a bare split — takes the untouched path, byte for byte, and no picture is cut. **This is an API ahead of its UI, and it is worth knowing before opening a project that has one.** Until phase E2 there is no gesture: nothing on the timeline cuts, and an edit is made by hand with `PUT /api/projects/{pid}/edit` (`{"keep": [[start, end], …]}`, replacing the whole list; `GET` reads it back with the source's and the output's length; `DELETE` goes back to keep-everything). A project carrying an edit shows the phase-3a timeline with its sentence blocks already **projected** — where the render will put them, holes closed, because the narration plan now answers in timeline seconds, with `duration` the output's length and an `edit` block saying which edit it projected through — **over a filmstrip and a waveform that are still drawn in source seconds**, so the blocks and the picture behind them disagree by the length of whatever was cut. Drawing the strip in timeline seconds, the range selection, ripple delete, the join marker, undo and the Render button are E2, and none of it exists. The routes follow the narration editor's rules exactly: the `GET` is allowed while a job holds the project, because it is a read; the `PUT` and the `DELETE` are a 409 while one does, and take the store's own lock around their read-modify-write, so a cut landing beside a per-sentence adjustment destroys neither (tested twenty times over on two threads); the body is strict (`extra="forbid"`; a boolean is not one second in) and a bad list is a 400 that names the range and stores nothing; a video that has not been transcribed is a 409, because the ranges are checked against the extracted audio's length and transcribing is what extracts it; and every write is audited as `project.edit` with the range count and the seconds removed — never the times, which would say where every cut is. Storing or clearing an edit also drops the memoised speaking rate, since that rate is measured over the sentences the render will speak and the edit decides which those are. Three refusals rather than silent wrong answers: an edit written by a different version of the app is refused rather than read as keep-everything (rendering the whole video while the user believes a cut is applied is the one thing this must never do quietly); an edit whose extracted audio has since gone is read back but neither applied nor ignored; and an edit that cuts every spoken sentence fails the job saying so. **One thing the Reviewer gate forced that a user would have felt:** `trim` is a filter and runs *after* the decode, so left to itself ffmpeg decodes every frame from the start of the file to the last kept range's end and throws most of them away — a 5 s keep at the tail of a two-hour recording would have been killed by a timeout sized to its 5 s of output. The picture step now seeks the input to the first kept range (`-ss` before `-i`, every trim offset by that origin; frame-exact — the decoded frames' `framemd5` is identical with and without the seek — and the tail keep on the corpus source fell from 3.9 s to 0.87 s), and its timeout follows **how far into the source the last kept range ends**, not the output length. It is also the one step of a re-voice that watches the cancel flag while ffmpeg runs, and Cancel kills the process rather than discarding its result when it is done; the job ends as cancelled with nothing rendered and nothing stamped. A render that applied an edit stamps `edit_rendered_at` beside `revoiced_at` (the output file keeps its name, so the cache-buster must move), and a whole-source run clears it, so the record never claims an edit the file does not carry. **One honest limitation, recorded rather than hidden:** `replace_video_audio` gained an explicit `video_duration` argument so the mux can be told an edited output's length — known before ffmpeg runs, as the sum of the kept ranges — instead of probing for it with the ffprobe the packaged app does not have. Everyone changes their own password under **Settings › Your account**. New and reset accounts — and the seeded `admin` on a fresh install — must set a password of their own at first login: the app shows a gate page instead of the studio, and the API refuses everything but the auth routes until the change is made (`403 password_change_required`), so `admin` / `admin` cannot survive first use from the UI or from a script.
