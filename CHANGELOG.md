## [Unreleased]

- [fix] **The narration timeline drew at zero scale the first time it was opened.** Found by driving the packaged app, and invisible to every gate before it: the types check, the unit tests pass and the view does render — it simply renders wrong, and only once. Everything on the timeline is positioned from the strip's measured width, and that measurement ran in an effect keyed on the tab becoming active. But on the render where it becomes active the view returns a **spinner**, because the narration plan is still being read, and a cold plan spends about ten seconds measuring the speaking rate. So the measurement ran against a ref that was still empty, returned early, attached no `ResizeObserver`, and — because nothing it depended on changed again — never ran a second time. The width stayed at zero and took every derived number with it: all sixty-two sentence blocks stacked at the left edge clamped to their three-pixel minimum, the waveform pooled to nothing, and no filmstrip at all, because its own effect bails when the picture is zero pixels wide and bails *silently*, that being a fallback rather than a failure worth a message. Leaving the tab and coming back put it right, which is exactly what made it easy to miss — by then the plan was cached, so the strip existed on the first active render and was measured normally. The measurement is a **callback ref** now, which fires when the node itself attaches whichever of the three early returns rendered before it, so there is no readiness condition left to keep in step with them.

- [fix] **One Import button on an empty Projects page, not two.** The page header carried an **Import** action at all times and the empty state carried its own **Import a file** button underneath it — so the one screen where somebody has nothing yet, and is least sure what to do, was the screen showing two primary buttons that do exactly the same thing, worded differently, a couple of hundred pixels apart. The **empty state's button is the one that stays**, because it is the better thing to reach for on a page with nothing on it: centred, in the tile the eye already goes to, and directly under the line saying which files are accepted. The header's copy is suppressed while that tile is up and returns the moment there is a project to sit beside, so there is exactly one Import on the page at any moment. It is gated on the projects query having actually answered rather than on the list merely being empty — during the first load it is empty too, and the button must not flicker out and back. This was the only place in the app where two such buttons collided: an `EmptyState` action elsewhere earns its place by going somewhere the page cannot otherwise reach (the Dashboard's **Open**), and the audit list and Docs pass no action at all.

- [feat] **The narration timeline: hear the whole re-voice before you run one** (porting vertical 5, phase 3a). The transcript card gains a **List / Timeline** switch. List is the editor phases 1 and 2 built — one textarea per sentence with its offset, mute, voice and speed — and it is unchanged. **Timeline** is a new view of the same sentences on one horizontal time scale: a filmstrip of the video across the top, the waveform of its original audio beneath it, and one block per sentence positioned at the moment the render will pin it and drawn as wide as the sentence was actually spoken, so a block sits over the burst of speech it belongs to and the empty space after it *is* the slack. A sentence carrying an offset also shows a **ghost outline at its original position**, so "what I moved" is visible without a second panel. The point of the view, though, is not the drawing — it is **Play**: the whole new narration, placed exactly as the render will place it, against the muted picture, **without running a re-voice**. That is the defect this closes. Until now the only way to hear what a timing adjustment did was to render the video again: the owner ran **six re-voices in twelve minutes on one 5m41s video**, each of them a full job, to find out how far to nudge one sentence, with no visual reference for how far that was. **What the audition costs, which the toolbar says rather than leaving to be discovered:** a cold one synthesises every sentence first, one row at a time with a progress count and a **Cancel** — several seconds for the first while the voice service warms up, then about a second each, three at a time. It is not paid twice: those clips are fetched through the same per-sentence preview route phase 2 added, so they are **the very entries the following re-voice reads out of the shared TTS cache**, and a sentence already auditioned is free to the render. Playback also starts before the whole narration is ready, on the contiguous run of clips that have arrived, because a pin is a floor and a clip landing in the middle would move everything after it. **There is no drag in 3a.** Offsets are still typed in the List view; the Timeline shows what they did, plays the result and lets a click on a block select it and seek the picture. Drag is phase 3b and is not built. Underneath are two new read-only routes on `api/routers/narration.py`, both deliberately allowed while a job holds the project — they write nothing, and refusing to let somebody look at or listen to a project during a re-voice would be a 409 on a read. `GET /{pid}/narration/plan` answers, for every sentence, the **effective** voice and speed the render will use, the window it has and whether it can be squeezed into it; the browser is left only the one piece of arithmetic that needs the decoded clips — where each one actually lands. That split is the design: the render's rate rules are answered from the very functions `_revoice_video` calls (`sentence_window`, `sentence_speed`, `per_sentence_speed`, `calibrate_tts_baseline`, all pulled to module level with the old methods kept as delegating seams) rather than written a second time in TypeScript, where they would be free to drift from the render the audition claims to be predicting. The audition **models the post-synthesis tempo squeeze** for the same reason — a clip more than 15% over its window is sped up to fit unless that would take more than 2x, and an audition that ignored it would report an overrun cascading through every later sentence that the render simply will not produce — and those two numbers ride in the plan instead of being copied into the client. `GET /{pid}/waveform` returns one magnitude per 125 ms bucket of the project's own `audio.wav`, read with the stdlib `wave` module and numpy in chunks: **no ffmpeg and no ffprobe**, neither of which the packaged app can rely on, and the duration everything is drawn against comes from the WAV header, because the strip and the blocks over it must share the scale of the file actually being drawn. It is computed once and cached beside the audio on that file's mtime and size, so a re-transcription invalidates it without anyone remembering to, and drawn as **one SVG path** rather than 2728 rects or a canvas. Three smaller things the Reviewer gate forced, each of which was the view telling a lie: a sentence whose offset pins it **at or past the end of the video** is marked as dropped and is **not** auditioned, because the mux is `-shortest` and the render will leave it out — playing it would be auditioning audio that cannot exist; the plan's speaking-rate measurement is **bounded** (past 45 s it answers with the engine's default rate rather than holding the request behind a page that says "Reading the narration…") and **memoised** per project, provider and voice, dropped whenever the transcript changes, because a tab reopened or a voice changed used to re-pay three syntheses every time; and a WAV whose header claims more frames than the file holds — a copy interrupted, a disk that filled — has its real end **found by bisection** and is drawn at the length that is really there, because the alternative was a confident flat band of invented silence over a stretch of recording we do not have, under sentence blocks the owner is aiming at it. One correctness trap worth recording because it is not obvious: **a URL is not a sufficient cache key for an audition.** The preview URL carries the voice and the speed but never the text, and it cannot — a sentence sitting on the speed floor or carrying an explicit per-sentence speed has a URL that does not move however it is reworded — so signing the decoded clips on the URL alone left a fixed Whisper mis-hearing playing the *old* audio, and its stale duration then mis-placed every sentence after it. The words are in the signature now. `services/narration.py` (`plan`, `baseline_rate`, `transcript_section`, `preview_url`), `services/waveform.py`, `services/processing.py`, `api/routers/narration.py`, and on the front end `frontend/src/components/project/TranscriptCard.tsx` (the extraction §6 of the spec called for in phase 2 and did not get) and `NarrationTimeline.tsx` over the pure helpers in `frontend/src/lib/timeline.ts`. The spec is `docs/porting/narration-timeline.md`, whose §7 now records what phase 3a shipped and what it changed about the design; **drag is phase 3b and per-segment translation phase 4, and neither exists**. Tests: `tests/test_narration_plan.py` (42), `tests/test_waveform.py` (26), vitest `lib/timeline.test.ts` (34), `tests/test_project_ownership.py` (+2 routes in the ownership sweep) — #narration-timeline
- [fix] **An interrupted copy into the synthesis cache could put a clipped sentence into every later video.** Both TTS generators finish a clip at the path they were handed and then mirror it into the shared cache, and both did that with a plain `shutil.copy` — a byte-by-byte write straight onto the shared key. The only completeness check anywhere is that the file exists. So a copy that stopped part way — the process closed, a job cancelled, a disk that filled — left a **truncated entry at that cache key permanently**: nothing sweeps `data/cache`, so every later preview of that sentence served the stump, and every later **re-voice** copied it out, saw a file, counted the sentence a success and muxed it into the finished video, straight past the failed-sentence counting added in 0.5.0 (`#revoice-failures`). This is **pre-existing render behaviour, not something the timeline introduced** — the render has always been able to lose that race with itself. What changed is the traffic: a browser GET now drives the same synthesis path, so a row's Play, a whole-transcript audition and a running re-voice can be filling the same keys at the same time, and a window that used to need a crash at the wrong moment is now merely narrow. Both generators publish through one helper now, `utils.helpers.publish_to_cache` — copy to a uniquely named `.part` file beside the key, then `replace_with_retry` onto it — so a cache key names either nothing or a complete clip, never a fragment. It **never raises**: the cache is an optimisation, and before this a copy error was swallowed by the generator's blanket `except` and reported as "this sentence produced no audio", failing a synthesis that had in fact succeeded. A racing writer that got there first is not an error either — the key is derived from the text, the voice and the speed, so an entry already sitting there is the same clip by construction. `replace_with_retry` itself moved from `services/projects.py` to `utils/helpers.py` (and is re-exported from its old home, so every existing caller and every test that patches `store.replace_with_retry` is untouched) because the generators live in `core/`, which may import `utils/` but must never import `services/`: the engine is the layer underneath. `core/edge_tts_generator.py`, `core/kokoro_tts_generator.py`, `utils/helpers.py`, `services/projects.py`; tests `tests/test_tts_cache_publish.py` (8), whose fake provider writes the way the real ones do — open, write, wait, write — so a half-written file is genuinely observable rather than appearing atomically and hiding the bug the test exists to catch — #tts-cache-publish
- [fix] **A finished re-voice would not play or download.** Every re-voice rewrites the same two files — `<stem>_revoiced.mp4` and its narration `.mp3` — in place, so the URLs serving them name a file whose bytes change underneath them while the address never does. Neither route sent a `Cache-Control` header, and a response without one may be cached on *heuristic* freshness (RFC 9111 §4.2.2: the browser is allowed to guess a lifetime from `Last-Modified` and answer the next request from its own copy without asking us). So the second re-voice onward was served the body cached from the first — and a cached body whose file has since been replaced does not play as the *previous* video, it fails to decode: a black frame stuck at 0:00, and a Download button handing over bytes that are no longer a video. It looked like the re-voice had failed when the job had in fact succeeded every time. Fixed on both sides, because either alone leaves a hole: the record now carries a `revoiced_at` stamp and the page hangs it on the media URLs (`?v=`) exactly as the generated-video player has always done with `rendered_at` — the re-voice side simply never had a stamp of its own — and the routes now send `Cache-Control: no-cache`, which does not forbid storing the file but does require revalidating it, so the `ETag` still earns a cheap 304 on the runs where nothing moved. The separate-track routes carry the same header: the narration is rewritten by every run just as the video is.

## [0.6.0] - 2026-09-16

A sentence that comes out in the wrong voice, or too fast, can be given its own before
the video is re-voiced — and heard on its own first, so a whole render is no longer the
only way to find out how a line will sound.

- [feat] **A sentence can be given its own voice and speed, and heard before the video is re-voiced** (porting vertical 5, phase 2). Phase 1 stored a per-sentence voice and a per-sentence speed and the re-voice already honoured both — but neither had a control anywhere in the app, so the only way to set one was to call the API by hand (`#narration-overrides`). Every transcript row now carries a **Voice** box and a **Speed** box beside the offset and the mute, and a **Play** button that speaks that one sentence: `GET /api/projects/{pid}/transcript/{index}/preview`, a new route beside the PATCH in `api/routers/narration.py`. Empty means "use the re-voice's own", and for the speed that is deliberately **not** the same as typing 1.0 — a stored speed is spoken at exactly that rate, skipping both the per-sentence fit and the post-synthesis squeeze, so the box carries a placeholder rather than a prefilled 1. What Play speaks is **the line as the render will speak it**, not a separate audition mode with its own rules: the words are the *stored* ones (the transcript editor has an explicit Save, so you can only hear what is saved — which is what lets this be a GET that writes nothing and stays honestly outside the audit guard), and the sentence's own voice and speed win over the Re-voice card's exactly as they win over the job at render time, so a call carrying nothing at all means "this line, the way the render will say it". The one field never taken from the sentence is the **provider**: the provider is the engine the job runs on and nothing in the render ever reads a segment's stored `provider`, so falling back to it would make the preview diverge from the render in precisely the case it claimed to help — a sentence holding a Kokoro voice under an Edge studio would have previewed in Kokoro and rendered in Edge. It is deliberately **not a job** (`services/jobs.py` allows one job per project, so a preview-as-job would block the very re-voice being auditioned) and deliberately **allowed while a job holds the project** — it writes nothing, and refusing a listen during a re-voice would be a 409 on a read. **What it costs, which the card says rather than leaving to be discovered:** about a second per sentence once the server is warm, about ten seconds for the very first press after it starts (the `edge_tts` import plus the first connection), and nothing at all on a repeat — the synthesis cache is keyed on (text, voice, speed), which is the **same key the render looks up**, so auditioning a sentence warms the cache the re-voice then reuses and nothing is synthesised twice; measured end to end against the real Edge service. The wait is bounded at 30 s and a provider that answers nothing becomes a readable 502 naming it, never a 500 and never Edge's own two-minute ceiling; Kokoro's model is **probed, never downloaded** — a 409 saying what to do about it, because one press of a Play button must not start a 340 MB download — and `services/voices.py` splits that sentence into its own constant so the voice list and the preview say the same thing about it. The voice control is a shared `<datalist>` type-ahead rather than a `<select>`: the provider's list runs to north of 300 voices (322 on Edge today), so a dropdown per row would put tens of thousands of `<option>` nodes into the page on a ten-minute video, and a list that long wants filtering as you type in any case. One hidden `<audio>` element serves every row, so a second sentence cannot talk over the first and pressing Play on the one that is playing stops it; a failed press renders its message **under the row that caused it**, because on a long transcript a single box at the top of the card is nowhere near the sentence. A committed box also keeps what was typed until its request settles — clearing it the moment the request was fired left one render with the draft gone and the saved value not yet back, so the box flicked to its old value and forward again — and a voice picked off the list saves at once, like the Mute tick, rather than waiting for a blur that may never come before Play is pressed. `services/narration.py` (`preview_segment`, `_synthesise`, `cache_path_for`), `api/routers/narration.py`, `services/voices.py`, `frontend/src/lib/narration.ts` (the pure rules: the URL, and what an emptied box means for each field, which differs), `frontend/src/pages/ProjectDetail.tsx`. The spec is `docs/porting/narration-timeline.md`, whose §7 now says what shipped and whose §5 has been corrected where the build proved it wrong; **the waveform, the drag and the timeline strip are phase 3 and still do not exist**. Tests: `tests/test_narration_preview.py` (29), vitest `lib/narration.test.ts` (10), `tests/test_project_ownership.py` (+1 route in the ownership sweep) — #sentence-preview
- [fix] **A preview could have put a clipped sentence into a finished video.** The preview was the only place in the app that let a TTS generator choose its own output path — and that path is the entry in the shared synthesis cache. Both providers write their audio **in place**, chunk by chunk, at whatever path they are handed, and the only completeness check anywhere is that the file exists: so the provider was streaming a network download straight into a file the rest of the app treats as finished. Two consequences, both reproduced before they were fixed. A second press during the first was served the half-written file as a clean 200. And a download that dropped part way left a truncated entry at that key **permanently** — the generator's own error path returns None without removing it, and nothing sweeps `data/cache` — which every later preview of that sentence then read, and so did every later **re-voice**, because the re-voice copies the cache entry out and checks only that a file exists. The sentence counted as a success, a clipped clip was muxed into the finished video, and the failed-sentence counting added in 0.5.0 (`#revoice-failures`) never saw it. Nothing is written to a cache path in the open now: the provider is handed a private `.part` file, unique per press, and the finished clip is published onto the cache path with an atomic rename, so that key names either nothing or a complete file. The rename is `services.projects.replace_with_retry` — the project save's own helper, made public rather than copied, because a second copy of a retry loop is a second thing to get wrong, and it brings the Windows sharing-refusal retry with it. Two smaller guards ride along: an empty result is refused instead of being handed back as a path to silence, and a zero-byte entry already sitting at the key is removed and made again. The honest limit is written down beside them — a truncated-but-non-empty mp3 can only be told apart by decoding it, that decode is ffmpeg, and paying it on every press to catch an entry this code can no longer create would be the wrong trade. `services/narration.py`, `services/projects.py`; held down by a test whose fake provider writes the way the real ones do (open, write, wait, write) so a half-written file is genuinely observable rather than appearing atomically and hiding the bug it exists to catch, and by a pin of the cache key against **both** real generators (Kokoro folds its active language into it) so a preview can never quietly write to a key nothing reads — #preview-atomic-cache
- [fix] **A refused preview says why, in the server's own words.** An `<audio>` element is told only that its source failed, so playing the clip by pointing the element at the route — which is what the spec called for, and what the existing video player proves works for cookies — would replace every message the route carefully writes with a guess: the 409 naming Kokoro's undownloaded model, the 400 naming a voice belonging to the other provider, the 502 naming the provider that answered nothing. Pressing Play is exactly the path someone takes to discover that a hand-typed voice id is wrong, so it is the place the reason matters most. The clip is fetched with the session cookie and played from a blob instead (`api.blob`, `frontend/src/api/client.ts`), so a refusal arrives as the same `ApiError` as every other call and the server's own `detail` reaches the page; building that error was lifted out of `request` into one `failure()` both call shapes share, so a failure reads the same wherever it came from and the 401 sign-out event still fires from a binary GET. Being a fetch also means **one request in flight at a time**: a second press while one is running is ignored rather than starting a second synthesis of the same sentence, and the button says "Speaking…" while it waits instead of looking broken. The only failure left on the element itself is audio the browser cannot decode, which has a message of its own — #preview-errors

## [0.5.0] - 2026-09-15

Every sentence of a transcribed video can be nudged or left out before it is re-voiced,
which is the answer to a narration that starts in the right place and finishes early.
The app also installs to a path with no spaces in it.

- [chore] **The app installs to `C:\Media-Studio-Enterprise`, with no spaces in the path.** The packaging name loses its spaces, which is the single value NSIS uses for the install folder, the Start menu entry, the Add or Remove Programs entry and the installer's own file name — so `Media-Studio-Enterprise_<version>_x64-setup.exe` installs to `C:\Media-Studio-Enterprise\` and every one of those reads the same. Spaces in that path have already cost this project a real bug: a self-restart died because Windows joins a command line without quoting it (`#fix-restart-spaces`), and the whole class is now simply absent. It is still a **per-user install with no administrator prompt** — a folder created under the drive root by a normal user is granted Modify for authenticated users, which is exactly what the in-app update and the project data need, so nothing about how the app writes to its own tree changes. The window title keeps its spaces; it is set separately. The first install picks the location, and every installer after it restores that location on its own (`RestorePreviousInstallLocation` in the generated NSIS). An existing install under `%LOCALAPPDATA%` is not moved — uninstall it, or leave it and it will simply go stale — #install-path
- [fix] **"Open data folder" would have stopped working anywhere but the original install path.** The desktop shell's file-opening permission was scoped to a literal `$LOCALDATA/Media Studio Enterprise/**`, so it matched only an install at that exact location: anyone who chose a different folder at install time got a shell whose **Open data folder** and **Save report** silently did nothing, with no error to explain it. The scope is `$RESOURCE/**` now — the resource directory the shell already resolves its own app root and data folder from — so the permission follows the install wherever it goes instead of naming a path that can stop being true — #opener-scope
- [feat] **A sentence can be nudged, or left out, before a video is re-voiced** (porting vertical 5, phase 1). Re-voicing pins every sentence to the moment it was spoken and turns the leftover time back into silence, which is why the picture stays in step (`#revoice-sync`) — and also why a narrator who spoke more slowly than the synthetic voice gets a re-voice full of gaps: 240 s of speech coming back as 169 s is not drift, it is 71 s of pauses faithfully reproduced. **Nothing here guesses a better rate**, and nothing ever will: the transcript now carries an **Offset** in seconds and a **Mute** box per sentence, so the one line that is wrong is moved by hand and the video re-voiced again. Each change saves on its own, at once (`PATCH /api/projects/{pid}/transcript/{index}`, a new router `api/routers/narration.py` beside the whole-list Save rather than another route on `projects.py`); a refused one — a 409 while a job holds the project, a 400 for a voice belonging to the other provider — puts the row back, instead of leaving the page showing a value the server never took beside an error box saying it did not. A per-sentence **voice** and **speed** are stored, validated and honoured by the render but have no control yet; that is phase 2. The adjustments live on the transcript segments inside the project's own `project.json`, not in a table and not in a map keyed by index: an index map has the worse failure, because re-transcribing changes the indices and would then apply somebody's offsets to *different* sentences, where on the segment a re-transcribe wipes them along with the sentences they belonged to — visible loss instead of silent corruption. Keeping them there had one sharp edge that had to be closed in the same change: the Save button posts the whole transcript back, `TranscriptSegment` had no `model_config` so pydantic's default `extra="ignore"` would have dropped the new keys on the way in, and `set_transcript` writes that list straight to disk — so every save of the *words* would have quietly deleted every adjustment on the project. That model is a text editor and now says so (`extra="forbid"`: an adjustment key in its body is a 422, never a silent drop), and `set_transcript` carries the adjustments across itself — by index, and only onto a segment that is still the same sentence's **window**, because the length of the list is not identity: a save that deletes one sentence and adds another keeps the count, and an index-only rule would slide every adjustment down a row onto a sentence it was never meant for. What cannot be carried is counted, returned as `timing_adjustments_dropped` and shown, rather than lost quietly. What an offset can promise is written on the card, because a pin is a **floor, not a position**: a sentence can always be pushed later, but pulling it earlier only moves it as far as the sentence before it finishes speaking. The re-voice honours all four — the pin moves by the offset (and by the *next* sentence's offset too, or the tempo squeeze fires against a window nothing will use), a muted sentence is dropped before the window maths so the sentence before it inherits its room and the last unmuted one still runs to the end of the video, an explicit speed is used verbatim and skips both the per-sentence estimate and the post-synthesis squeeze, and a per-sentence voice falls back cleanly when it belongs to the other provider. Muting every sentence is refused with a reason (400) rather than failing inside the job as a bare "Re-voice failed", and the re-voice card says plainly that the adjustments do not apply to a **translated** re-voice: translation joins the whole transcript into one block before it runs, so the engine re-cuts it and spreads the sentences across the video by length, and no sentence survives for them to belong to. `services/narration.py`, `api/routers/narration.py`, `api/schemas.py` (`SegmentOverride` — five fields, strict so a boolean is not coerced to 1.0), `services/processing.py`, `services/revoice.py`, `frontend/src/pages/ProjectDetail.tsx` and `lib/format.ts` (a separate `timecode()` in `m:ss.mmm`; `duration()` rounds to the second and is left alone). A new audit constant `project.transcript_timing` records who moved a sentence — field names only, never the sentence itself. The spec is `docs/porting/narration-timeline.md`, whose §7 now says what shipped; the waveform, the drag and the timeline strip are phase 3 and do not exist. Tests: `tests/test_narration_overrides.py` (25), `tests/test_revoice_sync.py` (+13), `tests/test_revoice.py` (+3), vitest `lib/format.test.ts` (+2) — #narration-overrides
- [fix] **Two edits landing together can no longer lose one — or destroy the project.** The whole-list transcript Save and a single-sentence adjustment are both a read-modify-write of the same `project.json`, and nothing held a lock they shared. The UI produces exactly that pairing: an offset commits when its box loses focus and the Save click follows it immediately. Two threads over 200 runs lost the adjustment 59 times, with both requests answering 200 and nothing logged to say so — and tore `project.json` once, which is the worse half: `get_project` answers None for a record it cannot parse, so the project fell out of the list and 404'd on every route while its video sat on disk referenced by nothing, and nothing in the app could ever have found it again. The lock now lives in `services/projects.py` **beside the file it guards** rather than in whichever feature needed one first — a lock owned by the narration editor would have protected the narration editor from itself and from nothing else — so `project_lock(pid)` is taken by the transcript Save, by the narration editor and by the delete, and is dropped with the project exactly as the slide editor's already was (`services/slides.py`'s lock is a different lock, for the engine's *inner* project.json). `save_project` is atomic too: a uniquely named temp file beside the record and `os.replace`, so a reader sees the record as it was or as it now is and never a fragment. That rename is retried with a short backoff, because on Windows it refuses with ERROR_ACCESS_DENIED whenever anything else holds either file for the instant it takes — a real-time scanner opening the file we have just written, the search indexer, a reader that opened it without `FILE_SHARE_DELETE` — measured at 2 failures in 60 runs of the concurrent loop before the retry and 0 after; POSIX never takes that path. Two more writers stopped saving stale copies: the transcribe and re-voice jobs now write onto the record as it is when they finish rather than the copy they read minutes earlier, so a transcribe no longer reverts a text edit saved while it ran and a re-voice no longer reverts an adjustment made since it started — the same re-read the generate route already did, and for the same reason. And now that it merges what is stored instead of overwriting it, `PATCH /{pid}/transcript` takes `jobs.require_idle` like every slide write does: a 409 while a job holds the project, which the transcript card renders. `services/projects.py`, `services/transcription.py`, `services/revoice.py`, `api/routers/projects.py`; the race is held down by a two-thread test run forty times in `tests/test_narration_overrides.py`, beside one that proves nothing half-written is ever visible — #project-record-lock
- [fix] **A sentence that fails to synthesise no longer disappears without a word.** The re-voice loop makes one attempt per sentence and moves on when it fails — unlike the deck path, which retries three times — so a whole line could be missing from the narration with nothing but a warning in the server log to show for it, and a generator that returned quietly having written no file did the same thing even more silently. Both are counted now, and so is a third case the adjustments introduce: a sentence whose offset pins it at or past the end of the video is not synthesised at all, because the narration is muxed with `-shortest` and it would not be in the render. The count comes back with the job (`failed_sentences`) and is kept on the project, so the page can still say "2 sentences could not be synthesised … re-voice again to try them once more" after the job id has been cleared; it is cleared on a clean run, because a stale number would go on claiming sentences are missing from a narration that has every one of them.
